# Currenta

AI-first news app: Flutter frontend, FastAPI backend (`backend/`), Supabase/Postgres+pgvector as the shared DB. See [README.md](README.md) for features/stack and [ARCHITECTURE.md](ARCHITECTURE.md) for the ingestion pipeline and recommendation logic.

## Structure

- `lib/` — Flutter app, feature-first (`lib/core/` for themes/config/network, `lib/features/` for Auth/News/Profile modules)
- `backend/` — FastAPI server (`backend/api/`), ingestion worker (`backend/worker.py`), AI/vector services (`backend/services/`)
- `supabase/` — DB migrations, schema, edge functions
- `admin/` — React + TypeScript admin portal (manual ingestion, DB explorer, analytics/trending); deploys to Cloudflare Workers (`admin.currenta.tech`) via `.github/workflows/deploy-admin.yml` on push to `main`. Superseded the vanilla JS/HTML/CSS version that lived at `admin-legacy/`, deleted 2026-08-24 once this had full parity and was confirmed live.
- `test/` — Flutter unit/widget tests; backend tests live alongside their modules as `backend/test_*.py`

## Build & Test

- Flutter: `flutter analyze`, `flutter test`, `flutter run --flavor dev --dart-define-from-file=config/dev.json` (the app has `dev`/`prod` Android product flavors — `--flavor dev` is required or Gradle produces `app-dev-debug.apk` but Flutter looks for the unflavored name and fails with "Gradle build failed to produce an .apk file")
- Backend: run pytest from repo root, e.g. `python -m pytest backend/test_ingestion_pipeline.py -q` (this specific file is also the pre-deploy smoke check run by `scripts/deploy-gcp.sh`)
- Local full-stack dev: `bash scripts/dev-start.sh` (Docker + ngrok + optional Ollama), `scripts/dev-stop.sh` to tear down

## Infrastructure

- **GCP Cloud Run is dormant as of 2026-08-20** — deliberately kept idle (cost vs. the app's current user count) rather than decommissioned, so it's ready to migrate back to if there's a user influx. It is **not** receiving deploys and its data is stale: the hosted `*.supabase.co` project it points at hasn't ingested since 2026-08-17 and is missing schema changes merged after that (e.g. the `articles.subcategories` column/taxonomy work). Don't treat anything read from Cloud Run or the hosted Supabase project as current — **the home server (below) is the only environment actually running right now**, for both dev and what functions as prod. `scripts/deploy-gcp.sh`/`backend/GCP_MIGRATION.md` still describe how to redeploy there when it's time to cut back over, but schema on the hosted project will need to be brought current first — **including checking for the same `user_profiles.interest_embedding` vector-dimension bug fixed on the home server 2026-08-24** (`supabase/migrations/20260824120000_fix_interest_embedding_dims.sql`, `20260824130000_fix_interest_vector_scalar_ops.sql`, `20260824140000_reconcile_article_embedding_dims.sql`): the column was created as `vector(768)` assuming Ollama nomic-embed-text, but `articles.embedding` had already been switched to `vector(1024)` (Voyage voyage-4-lite) via an out-of-band SQL Editor script, so every write into `interest_embedding` silently failed and personalized ranking never activated — confirmed on home server via `SELECT format_type(atttypid, atttypmod) FROM pg_attribute WHERE attrelid='user_profiles'::regclass AND attname='interest_embedding'` returning `vector(768)` while 0 of 13 profiles had a populated value despite real `article_likes`. Not yet checked against the hosted project (would need `DATABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` from this repo's `.env`, which back live auth for every currently-installed app build — treat that connection with the same care as any other prod credential, not as casually as the home server). If the same migrations need re-running there, note `update_user_interest_vector()`'s scalar-multiply also needs the `array_fill(scalar, ARRAY[dims])::vector` workaround from `20260824130000` — pgvector 0.8.2 has no `vector * float8` or any `vector / ...` operator, so the original function was invalid SQL independent of the dimension bug.
- **Supabase**: the home server's self-hosted stack (`db`/`auth`/`rest`/`storage` — Postgres+pgvector, GoTrue Auth, PostgREST, file-backed Storage; see `docker-compose.yml`/`Caddyfile`) is **live and cut over for dev** as of 2026-08-17. `dev-api.currenta.tech` (the home server's `api`/`worker`) now points `DATABASE_URL`/`SUPABASE_URL`/`SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY` at the self-hosted stack, and this laptop's `lib/core/config/app_config.dart` (gitignored, copy from `app_config.template.dart`) matches it. A full data migration ran: schema + all rows for `public.*` and `auth.users`/`auth.identities` restored via `pg_dump`/`pg_restore` from the hosted project, all ~8.7k Storage objects (article cover images) re-uploaded through the Storage API (not raw `pg_restore` — object metadata rows must be created by the same upload call that writes the file to disk, or the `version` id in the DB won't match what's on disk and reads 500 with `ENOENT`), and `articles.image_url` rewritten from the hosted domain to `https://dev-api.currenta.tech/storage/v1/object/public/...`. Extensions matched to hosted (`vector`, `pg_stat_statements`, `pgsodium`, `supabase_vault`, `pg_cron`, `pg_net` — deliberately not `pg_graphql`, unused in this codebase). Self-hosted-specific `anon`/`service_role` JWTs live in `.selfhost_keys` on the home server (gitignored, git-ignored path also added locally) — kept separate from the `SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY` env vars so a future full restore-from-hosted doesn't clobber them. See `supabase/self-host/init/` for the fixes baked into first-boot init (all fire on a fresh/wiped Postgres volume): a bogus `ALTER USER supabase_functions_admin` on a role that doesn't exist in this trimmed stack (aborted the rest of `roles.sql`, silently left `supabase_storage_admin` passwordless); `auth.uid()`/`auth.role()`/`auth.email()` pre-owned by `postgres` in the base image, blocking GoTrue's own migration until reassigned to `supabase_auth_admin`; `supabase_storage_admin` needing `GRANT anon, authenticated, service_role` for the Storage API's per-request `SET ROLE` to work; and the extensions list. `PGRST_DB_SCHEMAS` is trimmed to just `public` and PostgREST's Docker healthcheck was removed (`postgrest --ready` hard-requires `server-host: localhost`, incompatible with listening on all interfaces for Caddy — cosmetic only). The backend's asyncpg pool also needed `DB_SSL_MODE=disable` (new env var, `backend/core/db.py`) for self-hosted — hosted's pooler requires SSL (`ssl='require'` was hardcoded) but self-hosted `db` has none configured (`SHOW ssl` → `off`) over the private docker network. Setting it in `.env` alone isn't enough: docker compose does NOT blanket-pass `.env` into a container, only vars explicitly listed under that service's `environment:` — it has to be added there too (now is, for both `api` and `worker`), or the app silently falls back to the `require` default. **`api`/`worker` run with `uvicorn --reload` watching the whole mounted `/app`** — writing scratch/log files under the repo root (e.g. a migration script's output) will trigger spurious restarts; use `/tmp` inside the container instead. **GCP Cloud Run prod is deliberately NOT cut over** — it still points at the hosted `*.supabase.co` project. Real reason, not just caution: currently-installed app builds authenticate directly against whatever Supabase project is baked into their `app_config.dart` at build time (hosted, for every release shipped so far). If Cloud Run's backend validated JWTs against self-hosted's JWKS instead, every currently-installed app would get instant 401s on every API call with no client-side fix short of a new release. Don't repoint Cloud Run without accounting for that.
- **Home server ("homeserver")**: an Ubuntu box (24.04→ actually 26.04 LTS, hostname `laptop-server`) used for (1) news ingestion (the `worker` service), (2) the self-hosted Supabase stack above, and (3) as the backend when running debug builds of the app during development/testing. It is **not** the developer's laptop despite the hostname — that name is legacy.
  - To SSH in: `ssh michael@laptop-server`. The bare `ssh laptop-server` (no user) does not resolve. Key-based auth already configured, no password needed for SSH itself.
  - `sudo` on that box requires an interactive password — it is NOT passwordless. Any `apt install` / `systemctl` work needs the user to run it themselves or grant NOPASSWD explicitly.
  - The `docker-compose.yml` stack at repo root (`api`, `worker`, `redis`, `caddy`, `db`, `auth`, `rest`, `storage`) is designed to run persistently there (all services are `restart: unless-stopped`); deployed automatically on push to `main` via `.github/workflows/deploy-home-server.yml` (self-hosted runner on that box).
  - Public hostname exposure uses a Cloudflare Tunnel (Cloudflare-managed, not ngrok/port-forwarding). The published application route is `dev-api.currenta.tech` → `http://localhost:80` (Caddy), reused for both the FastAPI backend and the self-hosted Supabase path routes (`/auth/v1`, `/rest/v1`, `/storage/v1`) — not the bare `currenta.tech` domain (that serves an unrelated static marketing page).
  - GCP Cloud Scheduler jobs that trigger ingestion/trending on Cloud Run (`currenta-orchestrate`, `currenta-trending`) still run independently against the hosted project — expected now, since home server `worker` and Cloud Run ingest into different DBs (self-hosted vs hosted respectively) until Cloud Run is also cut over.
  - **2026-08-25 outage: Tailscale MagicDNS going unhealthy took down `dev-api.currenta.tech` entirely** (app showed "Failed to start guest session: error code: 1033", i.e. Cloudflare tunnel-down, and feed requests that did get through hung until the client's 30s timeout). Two separate DNS layers broke and both need checking/fixing — fixing only the first looks like a full fix (health checks pass, tunnel is up) but leaves the app silently broken: (1) **Host DNS**: `/etc/resolv.conf` on `laptop-server` is Tailscale-managed and pointed at MagicDNS (`100.100.100.100`/`fd7a:115c:a1e0::53`); it started returning `SERVFAIL` for every lookup (`journalctl -u tailscaled` showed `dns: resolver: forward: no upstream resolvers set, returning SERVFAIL`), which crash-looped `cloudflared` (`Couldn't resolve SRV record ... argotunnel.com`) since it couldn't resolve Cloudflare's edge. `sudo tailscale set --accept-dns=false` and even `systemctl restart tailscaled` did not repair it — the fix was directly overwriting `/etc/resolv.conf` with a working resolver (`sudo sh -c 'printf "nameserver 192.168.100.14\nnameserver 1.1.1.1\n" > /etc/resolv.conf'`, using the LAN router as primary since `resolvectl status` showed it already correctly configured on `enp2s0`), then `sudo systemctl restart cloudflared`. (2) **Container DNS**: fixing the host doesn't propagate to already-running containers — Docker's embedded resolver (`127.0.0.11` inside each container) caches the host's nameservers as `ExtServers` at container start and only re-reads them on restart (`docker exec currenta-api-1 cat /etc/resolv.conf` will show the stale broken `ExtServers` even after the host is fixed). This second layer is what actually broke the feed: it made the `api` container's own outbound calls fail (`[Errno -3] Temporary failure in name resolution` on the embedding API and Google Trends RSS in `docker logs currenta-api-1`), which specifically blocked the cold-start `interest_embedding` seeding path on a new guest user's first feed request — that request hung retrying the dead lookup (backend logs an exponential 2s→32s backoff) well past the Flutter app's 30s Dio receive timeout, so the request aborted client-side even though `/health` and other simpler requests were already returning 200. Fix: `docker restart currenta-api-1 currenta-worker-1` after host DNS is confirmed working (`nslookup google.com` returns real answers). Restarting `tailscaled` while SSH'd in over the tailnet drops the SSH session (tears down `tailscale0` mid-restart) — expected, just reconnect, or connect via the LAN IP instead to avoid the disruption. See `[[project_homeserver_tailscale_magicdns_outage]]` memory for the full timeline.
